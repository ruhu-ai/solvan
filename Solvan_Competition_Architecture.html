Solvan Architecture Reference · Fortified Enterprise Fleet

Autonomous Production Engineer

Solvan is a governed fleet of institutional agents that detects production degradation from events, investigates live evidence, executes bounded policy-authorized recovery, verifies the outcome independently, and owns a multi-day permanent-repair case — with every step durable, fenced, and receipted in Cloud SQL.

Architecture stance. Two planes with a hard boundary: the probabilistic plane (Gemini agents on Agent Runtime) investigates, ranks, and proposes; the deterministic plane (typed services over Cloud SQL) owns permissions, state transitions, budgets, approvals, idempotency, mutations, and verification. Model output can become a proposal — never authority.
Competition alignment. Sections 14–15 assess Solvan through the lens of Google's own training lab for this challenge — Build Long-Running Agents with ADK 2 (adk2003), "the ADK lab" throughout — mapping every mandated technology and every taught pattern to the enforcing mechanism and its named test. The lens demonstration runs on the release-gated payments slice; the submitted codebase goes further — most of the enterprise expansion is already implemented and locally verified beyond the lens, and the remainder is held as reviewed target contracts, each labelled as exactly what it is. Solvan is built for this competition and engineered to outlive it as Ruhu Inc.'s production reliability platform.

The Solvan Poster: Executive Architecture

The poster: one incident's journey (dotted path) crossing every subsystem — Event Driven at ingress, planned by the Supervisor, evidenced through governed tools, paused for a Human in the Loop, executed by the private actuator, Independently Verified, then held open for a week of Long Waits and Resumes with zero resident processes. Every product card is a mandated platform pillar; every guarantee chip is a named test in the durability and idempotency tables (Sections 04 and 10).

Runtime Contract

  • Incidents begin from events, not prompts; chat reads projections and requests work but never defines the lifecycle.
  • The coordinator creates every durable agent_run before dispatch; no agent invokes another agent directly.
  • Every transition uses expected-state + workflow-version CAS under a token-fenced lease; terminal histories are immutable.
  • Gemini investigates, ranks, plans, summarizes, drafts; typed application services own permissions, risk, budgets, and mutations.

Enterprise Control Points

  • Tenant/project/environment scope on every row; classification, purpose, and residency filtered before retrieval and again before prompts.
  • Operator-facing claims instantiate from a digest-pinned template registry; a failed predicate is withheld, never softened into prose.
  • Immutable histories with superseding records; dual-written receipts; independent verification shares nothing with the producer it judges.
  • Preview platform features carry tested degradation paths and are never the sole control on a consequential action.

Why rows, not resumed conversations

The ADK lab's own ResumabilityConfig note warns: "any temporary / in-memory state will be lost upon resumption." Solvan takes the warning to its conclusion: a half-finished model invocation is never trustworthy state. The unit of recovery is the durable agent_run; recovery is a fresh, fenced attempt rebuilt from authoritative rows, and idempotency constraints make repeated effects impossible rather than unlikely.

Suspension is a state, not a parked process

AWAITING_APPROVAL and scheduled_wakeups are Cloud SQL states with fenced claims and expiry — an 18-hour human pause or a 7-day case costs zero compute and survives any deployment. The stale-progress policy escalates abandoned work instead of letting it rot; case liveness rules make silent dormancy a schema violation.

Bounded invocation

  • Invocation JSON is the complete authority ceiling: scope, tools, deadline, budget, evidence refs.
  • Pinned input_hash/output_hash; single-turn; include_contents="none" isolation.
  • Deterministic loop enforcement outside the model: fingerprinted calls, progress checks, budget stops.

Untrusted by default

  • Logs, traces, repos, tickets, tool responses, model output, and Memory Bank content are data, never instructions.
  • Model Armor screens supported paths inline; verdicts persist on evidence and gate memory promotion (armor_verdict_ref NOT NULL).
  • Injection demo: a malicious log line stays evidence and cannot become instruction or memory.

Claims, not prose authority

  • Operator-facing factual claims instantiate from an enumerated, digest-pinned template registry.
  • The application derives kind, polarity, and sentence, and verifies the predicate in code against cited records.
  • A failed predicate is withheld or replaced by its holding form — never softened into fluent text.

The fleet graph, Solvan-style: agents on top, tool surfaces below, and one amber gate every call must cross. The supervisor deliberately has no edge to any tool — a planner that cannot touch the world cannot be prompt-injected into touching it.

Memory is earned, not accumulated. Memory Bank recall is exact-scope and non-authoritative. Promotion into durable memory requires type-specific confirmation rules plus a recorded armor verdict; unconfirmed or poisoned candidates are quarantined (test_unconfirmed_or_poisoned_candidate_is_quarantined, test_memory_candidate_promotes_once_and_retry_returns_durable_receipt).

Data, Memory, And Conversational Surface

Release schema · 61 tables

  • Incidents, cases, plans, steps, runs, tool calls, evidence, hypotheses, actions, approvals, reservations, receipts, transitions, wakeups, inbox/outbox, memory, workspaces.
  • Loaded from empty into PostgreSQL 16 in CI; constraint oracles assert negative cases; append-only audit triggers.

Operability schema · 54 tables

  • Governed Tool Catalog and capability profiles; Operational Guidance revisions with registered completion predicates; trigger policies; skills interchange records.
  • Status: implemented and locally verified, beyond the lens (specs 16–18) — guidance selection, tool-catalog wiring, and quarantined skills import run in real coordinator paths; cloud release qualification is deliberately not yet claimed.

Conversation schema · 34 tables

  • One canonical Liaison ledger across console and channels: read/steer grants, per-part access modes (empty set denies), durable delivery, compaction.
  • Identity from verified claims only; a read grant never proves write or steer authority.
  • Status: implemented and locally verified, beyond the lens (spec 14) — five channel liaisons with the Slack lifecycle, steer confirmation, subscriptions, and deterministic compaction.

Further target schemas beyond these two — alert triage (28 tables, implemented), outcome quality (17), production graph (16), connection scope (4), relay (18), SaaS scale (28) — bring the platform's schema surface to 260 tables.

Evidence with provenance

  • Every evidence item: source, window, query, hash, classification, residency, retrieval actor, freshness expiry, armor verdict.
  • Citations must resolve to stored records; an unresolvable reference renders inert and demotes the statement to inferred.
  • Validated vs inferred findings are visually and semantically distinct in the console.

Conversation reads, never mints

  • Chat and channel liaisons read reader-filtered projections of durable state; asking a question can never create a fact.
  • Approval by conversation surfaces the same digest-bound panel — inline text never becomes an approval.
  • Every durable conversational part declares an access mode; visibility is never granted by omission.
Skills without surrendering authority (target contract). The open Agent Skills format is adopted as a quarantined interchange profile: packages are hardened, scanned, and held as inert records; a human compiles them into governed guidance through evaluation and independent approval; scripts never execute; allowed-tools grants nothing; activation pins content and never fetches origins. Four adversarial review passes; 24 acceptance tests specified.

Enterprise Platform: Shown, Shipped, Specified

The honest enterprise claim, in three levels. What the lens demo shows is release-gated. What the submission ships goes further: most of the enterprise expansion is implemented and locally verified in this same codebase — it simply is not part of the lens demonstration, and its cloud release qualification is not yet claimed. What remains is specified: reviewed normative contracts with acceptance tests, not roadmap prose. Solvan is built for this competition and continues beyond it as Ruhu Inc.'s production reliability platform.

Deployment, Quality Gate, And Scoring Alignment

The ADK lab's step-10 topology — Cloud Run + Scheduler + Pub/Sub + Cloud SQL + GCS + Trace — with Agent Runtime carrying the model work and the governance plane wrapped around all of it.

Deployment topology

  • Cloud Run: coordinator, API, actuator, verifier, detector, evidence broker, publisher, liaisons, workspace services — each with its own service identity.
  • Agent Runtime: bounded agent executions as long-running query jobs against pinned reasoningEngines resources.
  • Cloud SQL (PostgreSQL 16): the authoritative ledger, region-pinned to europe-west1.
  • Pub/Sub + Cloud Scheduler: the only things that wake anything; push endpoints ingest, ticks drive.
  • GCS: evidence and runtime objects, hash-addressed; Cloud Trace: OTel spans correlated to domain rows.
  • Cloud Build: 22 immutable image outputs; deployment preflight validates agents, identities, gateway policies, and armor templates before release.

The ten-stage merge gate (scripts/check)

  1. Python lint and format
  2. Python types (mypy, 315 files)
  3. Architecture boundaries, agent manifests, Ruhu profile, Cloud Build contract
  4. Documentation and repository knowledge
  5. Executable schema + transition contracts on clean PostgreSQL 16
  6. Unit and harness tests with coverage
  7. Agent safety and trajectory evaluation
  8. Console types
  9. Console production build
  10. Browser critical path
